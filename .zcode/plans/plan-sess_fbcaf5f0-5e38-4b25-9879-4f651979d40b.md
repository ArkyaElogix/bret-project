# Access Control Fix + Candidate Portal

## Root cause (confirmed from the code)
- **Backend**: `forms`, `questions`, and `behavioural_types` routers have **NO auth dependency at all** on any endpoint — fully public. That's why candidates could create/delete forms. (`behavioural_factors` write endpoints already require admin; reads are public.)
- **JWT**: `create_access_token(user_id)` puts only `{"sub": user_id, "exp"}` in the token — **no role**. `POST /auth/login` returns only `{access_token, token_type}`. So the frontend can't know the user's role → `ProtectedRoute` only checks token presence → candidates roam freely into admin pages.
- This explains your test results exactly (e.g. could delete only *their own* new forms because `delete_form` blocks when sessions are attached, not because of any auth check).

## Decisions (per your answers)
- Candidate portal shows **active forms only**.
- Portal goes as far as **start-session + profile** this step (no full assessment-taking screen yet).
- Lock admin with **role-aware frontend gating** (add `GET /auth/me`, store role, hard-redirect non-admins).

---

## PART A — Backend (security hardening)

### 1. `backend/app/auth.py` — add role to the JWT
`create_access_token(user_id: int)` → `create_access_token(user: User)`, payload becomes `{"sub": str(user.id), "role": user.role.value, "exp": ...}`. (Decoding stays backward-safe — `get_current_user` already reloads the user from DB, which is the source of truth, so old tokens without `role` still work until they expire.)

### 2. `backend/app/routers/auth.py` — login response + `/auth/me`
- Update `login` to pass the `User` object to `create_access_token`.
- **Add `GET /auth/me`** → returns `UserOut` for the bearer-token owner (uses `get_current_user`). This is what the frontend uses to learn the role after login.
- Extend `TokenResponse` schema to include `role` (so login itself also returns the role, no extra round-trip needed).

### 3. `backend/app/schemas.py`
- Extend `TokenResponse` to `{access_token, token_type, role}`.

### 4. Lock down the open routers (add `Depends(require_admin)`)
- **`forms.py`** → `POST /` (create), `PUT /{id}` (update), `DELETE /{id}` (delete) become admin-only. `GET /` (list) and `GET /{id}` stay **public-but-authenticated** (any logged-in user) because candidates need to read the active form to start an assessment → use `get_current_user` there.
- **`questions.py`** → all write endpoints (`POST`, `PUT`, `DELETE`) become admin-only. `GET` endpoints (list/get) get `get_current_user` (candidates need to read questions of the form they're taking).
- **`behavioural_types.py`** → same: writes admin-only; `GET`s get `get_current_user`.

**Net effect**: candidates can READ forms/questions/sections (needed to take an assessment) but can no longer CREATE/UPDATE/DELETE anything.

### 5. `GET /forms/` filter (optional, small)
The candidate portal needs *active* forms. I'll add an `active_only: bool | None = None` query param to `list_forms`; the frontend passes `?active_only=true`. Admin page still gets all forms.

## PART B — Frontend (role-aware gating)

### 6. `frontend/src/api/client.ts`
Add `getRoleFromToken()` helper that decodes the JWT `role` claim client-side (no library — just `atob` on the middle segment). This gives an instant, synchronous role check for route guards without waiting on a network call.

### 7. `frontend/src/api/auth.ts`
- Add `getMe()` → `GET /auth/me` (returns `User`).
- Update the `login()` return type to include `role`.

### 8. `frontend/src/components/ProtectedRoute.tsx`
Split into two guards:
- **`AdminRoute`** — admin-only. If no token → `/login`; if token but role ≠ ADMIN → `/portal`. Used for all current admin pages.
- **`UserRoute`** (or reuse a simple token-check) for the portal.

### 9. `frontend/src/pages/LoginPage.tsx`
On successful login, branch on role: `ADMIN` → `/forms`; `USER` → `/portal`.

### 10. New: candidate portal
- **`frontend/src/components/PortalLayout.tsx`** — a distinct layout (its own header "BRET / Candidate Portal", a simple top nav with "Forms" + "My Profile" + Logout). Reuses the Tailwind conventions; no shared sidebar with admin.
- **`frontend/src/pages/PortalFormsPage.tsx`** (`/portal`) — lists **active forms only** (`listForms({ active_only: true })`). Each form has a "Start Assessment" button → calls `POST /sessions/start` (new `startSession()` in `api/sessions.ts`). On success, shows a confirmation ("Session started — assessment screen coming soon") since the full question UI is deferred.
- **`frontend/src/pages/PortalProfilePage.tsx`** (`/portal/profile`) — fetches `getMe()` and shows the user's email (their identity) + role. Read-only, as you noted only the email is stored.
- **`frontend/src/api/sessions.ts`** — add `startSession(formId, productType)` → `POST /sessions/start`.

### 11. `frontend/src/App.tsx`
Add routes:
- `/portal` (UserRoute) → `PortalFormsPage`
- `/portal/profile` (UserRoute) → `PortalProfilePage`
- Existing admin routes switch from `<ProtectedRoute>` → `<AdminRoute>`.
